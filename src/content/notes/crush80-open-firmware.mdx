[crush80-zmk](https://gitlab.com/ritwick7/crush80-zmk) replaces the closed firmware of the Wobkey Crush 80, a good keyboard, with ZMK, installed over the keyboard's own USB cable.

## A conditional layer killed my right Win key

A key is read from the highest layer that has something on it, and a transparent key falls through to the layer below. I once made a layer conditional: on only while Mac mode and Fn were both active. ZMK re-checks that rule after every layer change, so holding right Win turned the layer on and the rule turned it straight off. The numpad and the macro layer behind it never worked outside Mac mode. It is a plain held layer now.

## I read the chip wrong, then the LEDs

The main chip is marked with a batch code and a logo and nothing else. I took it for a WestberryTech WB32 and wrote a QMK board definition that could never have flashed.

The stock firmware settled it. Its USB string descriptor says `TLSR9511`, the code disassembles as RISC-V, and the peripheral accesses match the Telink B91 register map. ZMK runs on Zephyr, and Zephyr runs on the B91.

The LEDs went the same way. I saw SPI traffic in the binary and concluded the lighting was two AW20216S matrix controllers. Then I opened the case. Every LED footprint has pads marked DI, DO, V and G: a WS2812-class daisy chain. The firmware had been telling the truth; I had read it wrong. I now look at the board first.

## Timers ran fast until I changed one number

Zephyr counts a 32 kHz clock and divides it into ticks with an integer division. At the default 10000 ticks a second that is 3.2 cycles, which became 3, so tapping terms, macro delays and idle timeouts ran short. Measured against the host over 60 s, the clock read 1.0665 times real time before the change and 0.9998 after. At 8000 ticks a second the division is exactly 4.

## 88 keys, 154 LEDs and one RISC-V chip

| Part | Detail |
|---|---|
| MCU | Telink TLSR9511 (B91): RISC-V, 48 MHz |
| Matrix | 6 rows by 16 columns, 88 keys |
| LEDs | 154 on one chain: 92 under keys, 62 in the side bar and logo |

A factory block at the top of the flash holds the calibration and the Bluetooth address. The flashing tools refuse to write there.

## The stock updater has no signature check, and that is the install path

The stock updater is a Windows program that speaks a 64-byte USB HID protocol with a CRC at each end and no signature check. Stage one sends a small bridge image through it. Stage two has the bridge write MCUboot and the ZMK application into place.

Updating a keyboard that already runs ZMK takes about eleven seconds and starts from recovery mode. Fn+Esc erases the first sector of the running image, so MCUboot finds nothing to boot and waits on USB. My first version hung the board, because that sector also holds code the firmware was still running. The erase and the reset now run from RAM.

## OpenRGB and VIA work on ZMK too

It drives all 154 LEDs, OpenRGB gives per-LED control, and VIA over USB or ZMK Studio over Bluetooth edits the same stored keymap. Combos and hold-tap timings still need a reflash.

## One keyboard has run it, and two people did the hardest parts

The 2.4 GHz dongle protocol is proprietary and not supported, and the battery reading is not yet calibrated. One keyboard has run this firmware, and it is the one on my desk, every day.

It stands on Adam Yung's Crush80_ZMK, which got USB and Bluetooth up on this exact board first, and scholzri's rainy75-zmk, whose reverse engineering of the shared Telink platform goes far deeper than mine. Most of this repository's own code was written by an agent under my direction, and its README says so.
